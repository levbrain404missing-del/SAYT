# SAYT — демо-стенд регистрации и входа

Минимальный сайт с регистрацией, входом, восстановлением пароля и личной
страницей «вы вошли». Написан на чистом Node.js **без единой внешней
зависимости**: `node:http`, `node:sqlite`, `node:crypto`, `node:tls`.
Нет npm-пакетов, нет сборки, нет `node_modules` — один файл `server.mjs`.

Задумывался как временный стенд, поэтому намеренно простой. Но пароли,
сессии и токены сделаны по-взрослому (см. «Безопасность»).

## Что умеет

| Функция | Детали |
|---|---|
| Регистрация | имя, почта, пароль + повтор. Проверки: совпадение паролей, минимум 8 символов, формат адреса, уникальность почты |
| Вход | cookie-сессия на 7 дней |
| «Вы вошли» | при заходе уже авторизованным — страница кабинета: имя, почта, даты, кнопка выхода |
| Восстановление пароля | одноразовая ссылка со сроком жизни 30 минут |
| Смена почты | в кабинете, с подтверждением текущим паролем |
| Выход | завершает текущую сессию |

Вся вёрстка и CSS встроены в `server.mjs` — статику раздавать не нужно.

## Безопасность

- **Пароли не хранятся в открытом виде.** Только `scrypt` (N=32768, r=8, p=1)
  с индивидуальной солью на каждого пользователя. Формат записи:
  `scrypt$N$r$p$соль$хеш`. Сравнение — `crypto.timingSafeEqual`,
  устойчиво к атакам по времени.
- **Пароли не попадают в логи.** Ни при ошибках, ни при отладке.
- **Сессии.** Токен 32 случайных байта; в БД лежит только его `sha256`.
  Cookie — `HttpOnly`, `SameSite=Lax`, `Secure` (при `SECURE_COOKIES=1`).
  Утечка базы не даёт угнать живые сессии.
- **Токены восстановления.** Тоже только хешем, одноразовые, 30 минут.
  После смены пароля **все** прежние сессии пользователя завершаются.
- **CSRF.** Токен на каждой форме, проверяется на всех POST-запросах.
- **Ограничение попыток.** Вход — 8 за 15 минут (на пару IP+почта),
  восстановление — 5 за 15 минут и регистрация — 10 за 10 минут (на IP),
  смена почты — 6 за 15 минут (на пользователя).
- **Отсутствие утечки через ответы.** «Нет такого адреса» и «неверный пароль»
  дают одинаковый ответ — перебор почт по ответам сервера не работает.
- **Лимит тела запроса** 16 КБ.

### Чего здесь нет (осознанно, это демо)

- Нет подтверждения адреса при регистрации — аккаунт активен сразу.
- Нет 2FA.
- Rate limiting — в памяти процесса: сбрасывается при рестарте и не
  работает на нескольких инстансах. Для одного процесса достаточно.
- `SHOW_RESET_LINK=1` печатает ссылку восстановления прямо на странице.
  Это **демо-режим** на время, пока не настроен SMTP. В реальной
  эксплуатации обязательно `SHOW_RESET_LINK=0` и заполненные `SMTP_*`.
- Код отправки писем (`SMTP_*`) написан, но **на практике не выполнялся** —
  без реальных SMTP-кредов проверить его было нечем. При первом включении
  ожидайте возможных правок.

## Требования

- **Node.js 22+** (нужен встроенный модуль `node:sqlite`)
- опционально — обратный прокси с TLS (пример для Caddy в `caddy/`)

## Запуск локально

```bash
git clone git@github.com:levbrain404missing-del/SAYT.git
cd SAYT
cp .env.example .env

# сгенерировать секрет сессий и вписать в .env
openssl rand -hex 32

# для локального http-доступа:
#   SECURE_COOKIES=0
#   PUBLIC_URL=http://localhost:3100
mkdir -p data
node server.mjs
```

Открыть `http://localhost:3100`.

## Запуск как служба (systemd)

Пример развёртывания. Пути в примере — `/opt/stub-auth` (код)
и `/var/lib/stub-auth` (база, логи); замените на свои.

```bash
# 1. пользователь без оболочки и без домашнего каталога
sudo useradd --system --no-create-home --shell /usr/sbin/nologin stubauth

# 2. код и каталог данных
sudo mkdir -p /opt/stub-auth /var/lib/stub-auth
sudo cp server.mjs /opt/stub-auth/
sudo cp .env.example /opt/stub-auth/.env    # затем отредактировать!
sudo chown -R stubauth:stubauth /var/lib/stub-auth /opt/stub-auth/.env
sudo chmod 600 /opt/stub-auth/.env

# 3. служба
sudo cp systemd/stub-auth.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now stub-auth.service
sudo systemctl status stub-auth.service
```

Юнит ограничен по правам: `ProtectSystem=strict`, `ProtectHome=yes`,
`NoNewPrivileges=yes`, запись разрешена только в `/var/lib/stub-auth`,
`MemoryMax=300M`.

Затем прокси — см. `caddy/site.example.conf`. Правило для Caddy:
**backup → `caddy validate` → `systemctl reload` (не restart)**.

## Удаление

`scripts/uninstall.sh` снимает службу, вырезает блок из `Caddyfile`
(с бэкапом, валидацией и reload без restart), удаляет код, базу и
системного пользователя.

Домен и порт передаются переменными — они должны совпадать с тем, что
реально стоит в `Caddyfile`:

```bash
sudo SITE_HOST=reg.example.com SITE_PORT=443 bash scripts/uninstall.sh
```

Блок находится по комментарию-маркеру `# ВРЕМЕННЫЙ демо-стенд регистрации
(stub-auth)` (переопределяется через `MARKER=`). Если маркер или блок
`https://SITE_HOST:SITE_PORT` не найдены — `Caddyfile` не изменяется вообще,
скрипт сообщает об этом и завершается с ошибкой, не меняя файл.

## Структура

```
server.mjs                    всё приложение: роуты, БД, крипто, вёрстка, SMTP
.env.example                  пример конфигурации (реальный .env не коммитится)
systemd/stub-auth.service     юнит systemd с ограничениями прав
caddy/site.example.conf       пример блока обратного прокси
scripts/uninstall.sh          полное удаление со сервера
```

## Схема базы

SQLite, создаётся сама при первом запуске:

- `users` — `id`, `name`, `email` (UNIQUE), `pass_hash`, `created_at`, `updated_at`
- `sessions` — `token_hash` (PK), `user_id`, `created_at`, `expires_at`
- `resets` — `token_hash` (PK), `user_id`, `created_at`, `expires_at`, `used_at`
